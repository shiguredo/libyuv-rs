## 目的

`src/scale.rs` の `_12` / `_16` サフィックス付き関数群（4 組 8 関数）が同一の Rust 型シグネチャを持ちながら異なる libyuv 関数を呼び出しており、利用者が誤った関数を選択してもコンパイラが検出できない問題を解決する。ドキュメントと命名を改善し、12 ビットデータと 16 ビットデータの意味的差異を明確化する。

## 優先度根拠

Medium。誤った関数呼び出しが発生した場合、12 ビットデータに `_16` を適用すると値域引き伸ばし（0-4095 → 0-65535）が発生し、16 ビットデータに `_12` を適用すると上位 4 ビットがサイレントに失われる。型システムで防止できない安全性上の懸念がある。

## 現状

`src/scale.rs` には以下の 4 組の `_12` / `_16` ペアが存在する:

| _12 関数 | _16 関数 | Rust 入力型 | libyuv C 関数 |
|---|---|---|---|
| `i420_scale_12` (L130) | `i420_scale_16` (L166) | `I012Image` / `I012ImageMut` | `I420Scale_12` / `I420Scale_16` |
| `i422_scale_12` (L202) | `i422_scale_16` (L238) | `I212Image` / `I212ImageMut` | `I422Scale_12` / `I422Scale_16` |
| `i444_scale_12` (L274) | `i444_scale_16` (L310) | `I412Image` / `I412ImageMut` | `I444Scale_12` / `I444Scale_16` |
| `scale_plane_12` (L451) | `scale_plane_16` (L552) | `&[u16]` / `&mut [u16]` | `ScalePlane_12` / `ScalePlane_16` |

**問題**:

1. **同一 Rust 型で異なる意味論**: 各ペアは同じ Rust 型を受け取るが、`_12` は「`u16` の下位 12 ビットのみ有効」、`_16` は「`u16` の全 16 ビットが有効」という異なるデータ契約を持つ。この契約は `I012Image` の型名（「12bit」を示唆）と矛盾する（`_16` 関数は `I012Image` に 16 ビットデータが格納されている前提で動作する）
2. **コンパイル時検出不能**: 12 ビットデータに `_16` を適用、または 16 ビットデータに `_12` を適用してもコンパイルエラーにならない
3. **文書化不足**: `_12` / `_16` の意味的差異（下位 12 ビットのみ有効か全 16 ビット有効か）がドキュメントに記載されていない
4. **非対称性**: `uv_scale_16` は存在するが `uv_scale_12` は不在（libyuv C API の制約）

各ペアの内部実装は libyuv の異なる C 関数を呼び出しており、削除・統合は不可能。合計約 180 行の構造的に類似したコードが存在する。

## 設計方針

1. 全 8 関数のドキュメントコメントに以下を追記する:
   - `_12` 関数: 「`u16` の下位 12 ビットのみが有効。上位 4 ビットの値は libyuv により無視される」
   - `_16` 関数: 「`u16` の全 16 ビットが有効。12 ビットデータに適用すると値域が 0-65535 に引き伸ばされる」
2. 各 `_12` 関数のドキュメントから対応する `_16` 関数へのリンクを追加し、逆も同様に行う
3. 命名は libyuv C API との追跡性を維持するため現状のままとする（`I420Scale_12` → `i420_scale_12`）

将来的な改善として、12 ビットデータ用と 16 ビットデータ用に別の newtype（`U12Data` / `U16Data` 等）を導入しコンパイル時に誤用を防止する方式も検討に値するが、本 issue のスコープ外とする。

## 完了条件

- `cargo fmt --all --check` が成功すること

## 解決方法

1. `src/scale.rs` の全 `_12` / `_16` 関数（4 組 8 関数）のドキュメントコメントを以下のテンプレートで更新する:
   - `_12` 関数: 「`src` の `u16` 値は下位 12 ビットのみが有効。上位 4 ビットの値は無視される。全 16 ビットを使用する場合は [`_16` 版] を使用すること」
   - `_16` 関数: 「`src` の `u16` 値は全 16 ビットが有効。下位 12 ビットのみが有効なデータには [`_12` 版] を使用すること」
2. 内部コード（FFI 呼び出し、検証ロジック）は変更しない
3. `CHANGES.md` に `[UPDATE]` エントリを追加する
